# Cite & Seek — Project Brief

**Meena P.** · INFO 7375 Final Project · Repo: [github.com/meenuviji/cite-and-seek](https://github.com/meenuviji/cite-and-seek) · Stack: Python 3.12, uv, sentence-transformers, numpy, Anthropic API

## 1. What is it?
Cite & Seek answers questions about one open-source codebase, cites the exact file and lines behind each claim, and says so when the code does not contain the answer. When it is done, it will be a public GitHub repository with the pipeline, a fixed evaluation set, an evaluation harness, an experiment log and a deployed demo.

## 2. Why would anyone care?
My hypothesis is that on a real team, this would help a new engineer understand unfamiliar code without pulling a senior engineer away from their work, and every answer can be checked. I haven't tested that with real engineers yet. The alternative today is reading the code by hand: that's how I checked every answer in my test set, and it's slow, and nothing tells you when you've missed the right file. Cite & Seek gives a file and line range for every claim. Its 53-question test set, 8 of which have no answer in the code, was written and checked before any retrieval code existed, so refusing is tested as well as answering.

## 3. Who opens it, and what do they do with it?
It's for someone hiring an entry-level AI engineer; the reader is a hiring manager or engineer reviewing a portfolio. In the first sixty seconds (once v1.0 ships) they will open the README, see the baseline compared with each experiment, with raw counts and confidence intervals, and check one query's cited lines in the source.

## 4. What does it prove about me?
- **Prompt contracts:** the v0.1 prompt requires only retrieved chunks, a `[path:start-end]` citation for every claim, or a single `ABSTAIN:` line, never a partial answer.
- **Verification:** the gold answers were checked by reading the code, not generated by an LLM.
- **Source grounding and evaluation:** the v0.2 harness will score retrieval (recall@k, hit@k, MRR) and answers (an LLM judge checked against my own hand labels), against a closed-book baseline.
- **Agent loops:** deliberately out of scope.

A reviewer could fairly conclude that I can design an evaluation before a system. They could not conclude production-scale RAG (one small repo, 53 questions), or that answers are faithful to their sources: the judge measures agreement with the reference answer, a gap I have logged.

## 5. What is in, what is out, what comes first?
- **In:** 37 files from [`Franklindot04/ecommerce-api`](https://github.com/Franklindot04/ecommerce-api) (MIT, © 2025 Ajero Franklin), including 10 synthetic incident reports.
- **Out (deliberately):** agents, fine-tuning, and orchestration frameworks such as LangChain, so every retrieval step stays visible.
- **First:** the v0.2 evaluation harness. You'll know it ran when a committed results file for the v0.1 baseline rebuilds with one command.

## 6. What could sink it?
The sample is small: after a fixed 80/20 split, only about 6 unanswerable questions remain for tuning, so one refusal moves the rate by about 17 points. I will report raw counts and 95% confidence intervals, and keep the held-out 20% untouched until v1.0.

## 7. Why this project?
Evaluation isn't new to me: I compared forecasting models on held-out data in my internship. What's new is retrieval, embeddings, and using one model to judge another. This project is how I learn those in a way someone else can check.
